## 1. Item-KNN 학습 게임 범위

### 확인된 데이터

테스트 계정과 검증 계정을 제외한 Kieran 학습안에서 집계했다. 아래 수치는 **긍정 사용자–게임 관측 수**이며 공동 긍정 게임 쌍이나 이웃 그래프의 간선 수가 아니다.

| 선택지 | 긍정 관측 수 | 장점 | 단점·주의점 |
|---|---:|---|---|
| 모든 Kieran 게임 | 84,791,317 | 향후 카탈로그 밖 게임을 사용자 입력으로 받을 때 그 게임과 Linux 후보의 연결을 활용할 수 있음 | 현재 입력은 카탈로그 안으로 한정돼 있어 추가 게임의 효과가 제한적. 앱 열과 이웃 관리 비용 증가. 전체 앱에서 먼저 이웃을 자르면 외부 앱이 필요한 내부 이웃을 밀어낼 수 있음 |
| **고정 입력 37,610개 게임** | **78,315,268** | 전체 학습 긍정의 92.36%를 유지. 비Linux 게임을 좋아한 이력으로 Linux 후보를 찾을 수 있음. 현재 평가와 범위가 일치 | 오래된 고정 카탈로그에 한정됨. 외부 게임이나 최신 게임 입력을 추가하려면 범위를 다시 설계해야 함 |
| Linux 후보 6,630개 게임만 | 27,581,735 | 행렬과 이웃 범위가 작고 Linux 내부 분석이 간단 | 비Linux 입력 게임과 Linux 후보 사이의 연결을 잃음. 사용 가능한 긍정 입력이 줄어들 수 있어 입력 적격성과 지원을 다시 집계해야 함 |

**고정 입력 카탈로그 37,610개 안에서 학습하는 것으로 확정했다.** 비Linux 게임도 학습·취향 입력에 포함하고 최종 추천 후보만 Linux로 제한한다.

### 전체 게임이 항상 더 좋은 것은 아닌 이유

현재 단순 공동 긍정 이진 코사인에서 게임 i와 j의 유사도는 다음과 같다.

```text
sim(i, j) = 두 게임을 모두 긍정한 학습 계정 수
            / sqrt(게임 i 긍정 계정 수 × 게임 j 긍정 계정 수)
```

같은 학습 계정과 내부 게임의 관측을 유지한 채 **외부 게임 열만 제거하면**, 내부 게임 쌍의 분자·분모는 바뀌지 않는다. 따라서 모든 게임과 카탈로그 제한 사이의 **내부 게임 코사인은 이 조건에서 동일**하다. 이는 코사인의 수학적 성질이며 성능 실험 결과가 아니다.

전체 앱을 사용한 사용자별 가중치·정규화, 사용자 필터링, 이웃 top-K 선택 순서가 달라지면 이 동등성이 깨질 수 있다. 현재 평가에 없는 외부 게임을 추론 입력으로 추가하는 경우도 점수가 달라진다. 앱 범위와 이웃 필터·절단 순서를 manifest에 함께 기록해야 한다.

### 긍정 게임이 하나뿐인 사용자는 유지할지

카탈로그 안에서 긍정 게임이 하나뿐인 학습 계정은 **17,042,189명**이다. 이들을 제거하면 관측 수가 78,315,268에서 61,273,079로 줄어든다.

- **유지:** 아이템의 전체 긍정 계정 수를 보존한다. 이 계정들은 게임 간 공동 긍정 분자에는 기여하지 않아도 코사인 분모에 기여한다. 구현에서 사용자 행을 처리하는 비용은 남는다.
- **제거:** 함께 긍정한 게임이 있는 계정에 계산을 집중할 수 있다. 하지만 아이템 빈도·정규화가 달라지므로 단순한 계산 최적화가 아니라 모델 변경이다.

확정안은 **아이템 빈도·정규화에는 singleton을 유지**하는 것이다. 공동 긍정 분자 계산에서 불필요한 singleton 쌍 연산을 생략하더라도 분모는 전체 해당 긍정 계정 수로 계산할 수 있다. 단, 실제 성능·실행 비용은 구현 뒤 검증해야 한다.

## 2. 실제 소개글 원문 구성

### 원문 선택지 비교

현재 고정 입력은 37,610개, Linux 후보는 6,630개다. 공백을 제거한 뒤 비어 있지 않은 문자열을 세었으며, 이 표의 수치는 원문 기준이며 토큰화 후 지원 검사와는 구분한다. 이후 수행한 영벡터 검사는 [콘텐츠 준비 결과](tfidf_content.md)에 기록했으며 자동 언어 품질 인증은 적용하지 않았다.

| 선택지 | 입력 원문 보유 앱 | Linux 원문 보유 앱 | 장점 | 단점 |
|---|---:|---:|---|---|
| A `description`만 | 36,993 | 6,507 | 출처 하나로 관리가 단순하고 현재 카탈로그와 연결이 쉬움 | 입력 617개·후보 123개 결측. 보충 가능한 정보를 놓침 |
| C `short_description`만 | 33,025 | 6,096 | 짧은 소개글을 한 출처에서 사용. C의 2025-03 수집 스냅샷으로 추적 가능 | 입력 4,585개·후보 534개 결측. 최신 수집 시점만으로 문장 품질 우위를 보장하지 않음 |
| **A 우선 + C 짧은 소개글 보충** | **37,531** | **6,613** | 입력 99.79%·후보 99.74% 원문 확보. A/C 짧은 소개글의 길이 중앙값이 211자·212자로 비슷함 | 서로 다른 수집 시점 혼합. A가 존재하면 C의 갱신 내용을 사용하지 않음. 짧은 문장에 게임 특징이 충분히 없을 수 있음 |
| C `about_the_game` 우선 + A 보충 | 37,528 | 6,613 | 더 자세한 메커니즘·세계관·플레이 설명을 포함할 가능성 | 긴 글과 짧은 글의 정보량 차이, 홍보 문구·반복 표현 영향. 특징 수·연산량이 늘 수 있으나 정확한 증가량과 성능은 미측정 |

마지막 행에서 우선순위를 반대로 하면 원문 보유 앱 수는 같아도 실제 선택되는 텍스트가 달라진다. C 긴 소개글 중앙값은 **1,142자**이며, 길다고 추천 품질이 더 높다고 결론 낼 수 없다.

두 짧은 소개글이 모두 있는 32,487개 중 **28,707개(88.36%)**는 앞뒤 공백 제거 후 정확히 같다. A 우선·C 짧은 소개글 보충은 A에서 빠진 입력 **538개**, Linux 후보 **106개**를 채운다. 최종 원문 결측은 입력 **79개**, 후보 **17개**다. 서로 다른 앱이 같은 소개글을 갖는 경우에는 텍스트 중복을 기록하되 앱을 같은 게임으로 임의 병합하지 않는다.

### 확정안과 필요한 전처리

**A `description` 우선·결측 시 C `short_description` 보충을 첫 베이스라인으로 확정했다.** 결측은 null·빈 문자열·공백뿐인 문자열을 포함한다. 자료의 정보 단위를 맞추고 높은 가용성을 얻는 출발점이며, 긴 소개글보다 성능이 좋다는 검증 결과는 아니다. 태그·장르는 기존 합의대로 후속 실험이다.

원문을 모델 입력으로 만들 때는 다음을 기록한다.

- App ID, 원문 필드, 출처 파일·버전·SHA256, 정리 규칙과 정리된 텍스트. 원문은 보존한다.
- 공백·HTML·엔티티·반복 홍보 문구·완전 중복과 텍스트 언어. 게임의 `supported_languages`는 소개글 자체의 언어를 보증하지 않는다.
- **원문 없음 / 전처리 후 빈 문자열 / 토큰화 후 영벡터**를 구분한다. 존재 여부 플래그만으로 TF-IDF 입력을 대신하지 않는다.
- TF-IDF 어휘·IDF를 계산할 문서 집합은 입력용 비Linux 게임을 포함한 고정 게임 텍스트로 명시한다. 모든 게임은 같은 어휘·IDF·정규화로 변환한다.

TF-IDF의 L2 정규화는 벡터 길이를 맞추지만 긴 글의 어휘·주제·정보량 차이를 없애지는 않는다. 토큰화·`min_df`·`max_df` 등은 내부 검증으로 선택하며, 단어를 제거한 뒤의 실제 지원 범위를 다시 집계한다.

여기서 고정된 공개 게임 메타데이터는 추천 시 이용할 수 있는 카탈로그 특징이다. **테스트 사용자의 리뷰·라벨을 학습에 섞는 것과 구분**한다. 현재 카탈로그를 공유하는 평가에서는 이 특징 집합을 미리 고정할 수 있다. 향후 미관측 신규 게임 평가나 과거 시점 예측을 하면 어휘 학습 범위·메타데이터 시점 정책도 달라져야 한다. A의 익명 사용자 이력과 C의 평점·리뷰 수는 소개글 입력에 합치지 않는다.

## 3. 공통 분할·점수 규칙

계정 단위 분리, 긍정 Linux 정답 1개 균등 무작위 숨김, 두 모델의 같은 사용자·정답·후보에 더해 아래 최소 입력·집계·빈자리 규칙도 확정했다. 다른 선택지는 비교 이력과 후속 실험으로 남긴다.

### 3-1. 최소 입력 조건

모든 조건은 **정답을 숨긴 뒤 남은 게임 수**다. 전체 입력은 긍정·부정을 합산한다. 조건을 통과하면 남은 적격 이력을 전부 유지하며 5개만 뽑는다는 뜻은 아니다.

| 선택지 | 잠재 사용자 | 장점 | 단점 |
|---|---:|---|---|
| 전체 ≥1, 긍정 ≥1 | 78,228 | 규모가 크고 이력이 적은 사용자도 포함 | 한두 게임으로 취향을 추정하는 사례가 많아 입력 부족의 영향이 큼 |
| 전체 ≥3, 긍정 ≥1 | 38,549 | 규모와 활동 이력 조건의 절충 | 여전히 긍정 입력은 한 개뿐일 수 있음 |
| **전체 ≥5, 긍정 ≥1** | **24,342** | 기존 EDA와 연결이 쉽고 개인화 단서를 최소 하나 보장 | 전체 5개가 취향 단서 5개를 뜻하지 않음. 긍정 1개+부정 4개도 포함 |
| 전체 ≥5, 긍정 ≥5 | 18,609 | 좋아한 게임이 여러 개라 취향 집계 근거가 풍부함 | 활동적·긍정 리뷰가 많은 사용자에 더 치우침. 이력이 적은 사용자 성능을 대표하지 않음 |

확정 베이스라인은 **전체 ≥5·긍정 ≥1**이다. 5개는 이 프로젝트의 EDA 연속성을 위한 출발점이며 일반적인 최적 기준으로 검증된 값은 아니다. **전체 ≥3·긍정 ≥1**은 후속 백로그로 등록했다. 기본 집단 안에서 긍정 입력 수별 성능도 진단한다. 위 값은 EDA 잠재 규모이며 최종 manifest 인원이 아니다.

전체 ≥5 집단 중 긍정 입력이 없는 **229명**은 기본 평가에서 공통 제외한다. 대신 이 사용자에 대한 결과는 다루지 못한다. 기존 테스트 예약 87,573명은 평가 집단 축소 후에도 학습·검증에 되돌리지 않는다.

### 3-2. 긍정 게임들의 점수 집계

| 선택지 | 장점 | 단점·추가 비용 |
|---|---|---|
| **동일 가중 평균** | 단순하고 재현 가능. 추가 취향 가중치 튜닝이 없음. TF-IDF와 Item-KNN의 해석을 맞추기 쉬움 | 여러 취향을 평균하면서 특정 관심사가 희석될 수 있음 |
| 후보별 최대 유사도 | 좋아한 게임 하나와 강하게 닮은 후보를 찾기 쉬움 | 우연히 높은 유사도나 반복 문구 한 건에 민감하고 여러 게임의 공통 지지를 반영하지 못함 |
| 최신성·플레이 시간 등의 가중 평균 | 단서의 중요도 차이를 반영할 수 있음 | 가중치와 기준 시각을 정해야 함. 현재 frank 리뷰 투영에는 플레이 시간이 없어 해당 방식은 추가 열 준비도 필요. 성능 개선은 미확인 |

확정한 동일 가중 평균은 TF-IDF에서 **각 게임 벡터 L2 정규화 → 남은 긍정 게임 벡터 평균 → 후보와 코사인**이다. 같은 조건의 후보별 코사인 평균과 사용자 내 순위가 같다. Item-KNN은 **각 긍정 입력 게임과 후보의 유사도 합 / 전체 긍정 입력 수**를 쓴다. 연결이 없는 기여는 0으로 두고 후보마다 분모를 바꾸지 않는다. 플레이타임 가중평균·최신성 가중평균 등 집계 변경은 후속 백로그다.

후보마다 연결된 이웃 수로만 나누면 근거 하나의 높은 유사도가 과대평가될 수 있다. 전체 긍정 입력 수가 고정이면 합계와 평균도 사용자 내 순위가 같으므로 이를 별도 순위 개선으로 취급하지 않는다. 실제 점수가 없는 사용자·게임은 다음 처리 규칙과 연결한다.

### 3-3. 지원 부족과 대체 추천

| 선택지 | 장점 | 단점·해석 |
|---|---|---|
| **개인화 점수만으로 추천하고 부족한 자리는 비움** | 모델 자체의 추천 근거와 한계를 직접 보여줌. 순수 모델 비교에 적합 | Top 10이 완성되지 않을 수 있어 실제 서비스 경험은 불완전 |
| 개인화 추천 후 학습 인기도로 빈 자리 채움 | Top 10을 제공하기 쉽고 두 모델에 같은 보완 규칙 적용 가능. 테스트 이력 없이 계산 가능 | 최종 결과에 인기도 효과가 섞임. frank 전체 기준선에서는 인기도가 무작위보다 낮아, 이 보완이 좋은 품질이라고 미리 보장할 수 없음 |
| 개인화 추천 후 고정 seed 무작위로 빈 자리 채움 | 개인화 근거가 없는 추천의 기준점을 확인하기 쉬움 | 개인화 이유가 없고 서비스 품질을 보장하지 않음. 과학적 비교용 보조 조건에 적합 |

**베이스라인은 개인화 점수만으로 추천하고 부족한 자리를 비우는 것으로 확정했다.** 양수 점수 후보를 최대 10개 반환한다. 적격 사용자에게 빈 목록이 나와도 지표 분모에 유지하며, 정답을 회수하지 못하면 Recall@10·NDCG@10은 0이다. 모델 성능 개선 후 학습 인기도로 빈자리를 채우는 방안을 검토하도록 후속 백로그에 넣었다.

후속 인기도 보완을 실험한다면 인기도는 **Kieran train의 긍정 계정 수**로만 계산한다. 긍정 점수 후보를 먼저 순위에 두고 부족한 자리만 채운다. 남은 긍정·부정 입력 게임은 제외하며 **숨긴 정답은 항상 후보에 유지**한다. 보완 사용자 비율·보완 슬롯 비율·보완 적중 기여도 분리한다. 현재 베이스라인에는 이 보완을 적용하지 않는다.

인기도 대 무작위의 기존 수치는 전체 평가 집단의 기준선이다. 실제로 보완이 발동하는 사용자·후보의 조건부 분포에서 어느 방식이 더 좋은지는 아직 계산하지 않았다. 지표를 좋게 만들기 위해 모델마다 미지원 정답이나 사용자를 제거하지 않는다. 공통 지원 집단만 보는 분석은 범위를 명시한 보조 결과로 구분한다.

### 3-4. 저장과 검증까지 규칙으로 포함

고정 seed만으로는 라이브러리 버전·행 순서·후보 정렬·자료 변경의 영향을 모두 막을 수 없다. **실제로 선택된 정답과 query, 적격 사용자, 앱 목록, 제외 마스크 규칙, 소스·코드·전처리 지문**을 저장해야 한다. 사용자별 정렬된 정답 후보와 재현 가능한 추출 규칙을 사용하고, 같은 명단을 두 모델에서 다시 읽는다. 숫자 seed는 **20261107**로 기록했고 실제 명단도 저장했다.

저장 파일을 다시 읽어 학습/검증/테스트의 원 Steam 계정·원 리뷰·사용자–게임 교집합, query–target 교집합, 정답의 긍정·Linux 조건을 검사한다. 같은 게임의 다른 계정 리뷰나 공개 게임 메타데이터 공유는 계정 누수와 구분한다. Kieran 내부 검증에서 설정을 선택하고 frank 모델 성능을 보고 설정을 조정하지 않는다.

## 4. 격리 손실과 모델 지원 상태

### 확인된 손실과 선택지

Kieran에서 모호 리뷰 332,865개 ID·686,161행이 63개 앱에 집중됐다. 55개 앱은 **원본 투영에 관측된 리뷰 행 전부**가 격리됐고, 63개 모두 90% 이상을 잃었다. Steam 전체 이력이 모두 없다는 뜻은 아니다.

326,403개 ID는 비교 가능한 필드가 앱 ID 외에는 같지만, 6,462개는 다른 필드도 다르며 라벨 충돌도 2개 있다. 따라서 모든 리뷰를 단순 복제로 간주할 수 없다.

| 선택지 | 장점 | 단점·적합한 용도 |
|---|---|---|
| **격리 유지 + 손실·지원 상태 보고 — 확정** | 검증되지 않은 앱 연결이 학습·정답에 들어가는 것을 막고 현재 감사 결과를 재현하기 쉬움 | 일부 정상 관측까지 보수적으로 잃을 수 있음. 특정 게임의 협업 근거 손실을 받아들여야 함 |
| 독립적인 앱 연결 근거가 있는 리뷰만 복구 | 정확한 근거가 확보되면 게임별 학습 지원 회복 가능 | 원 게시물·공식 연결 등 조사 비용. 앱·원 리뷰·라벨 충돌·버전과 계정 분리 재검증 필요. 근거가 확보된 부분에 한해 후속 작업으로 적합 |
| 카탈로그에 남은 앱으로 일괄 배정 | 복구 규칙이 간단하고 카탈로그 앱이 하나인 22개 조합의 329,756개 ID를 활용할 가능성 | 카탈로그는 프로젝트의 선택 목록이지 올바른 원 앱의 증거가 아님. 틀린 연결을 대량으로 확정할 위험이 있어 비권장 |
| 관련 게임을 평가 후보에서 공통 제거 | 깨끗한 지원 조건에 한정한 비교가 단순해짐 | 어려운 사례를 제외해 평가 범위가 바뀜. 기존 카탈로그 전체 성능을 대표하지 않으므로 기본 평가보다 보조 민감도 분석에 적합 |

복구하려면 원 리뷰 ID와 계정, 원래 앱 연결을 독립 근거로 확인하고 근거의 URL·확인일·매핑 버전을 남겨야 한다. frank의 정답 라벨을 이용해 Kieran 학습 라벨까지 맞추지 않는다. 복구 원본과 변경 내역을 보존하고 정제 버전을 올린 뒤 기존 계정 제외부터 다시 검증한다.

Kieran 전체의 모호 리뷰 집합과 **frank용 296개 모호 리뷰 참조 목록은 범위가 다르다.** 같은 파일이나 같은 개수로 간주해 한쪽만 필터링하면 안 된다. 소스별 격리 이유와 적용 범위를 기록해야 한다.

### 모델별 지원 상태를 기록하는 장단점

Linux 후보 6,630개 중 학습 긍정 0명은 36개, 1~4명은 188개, 합쳐서 5명 미만은 224개다. 전체 입력 ≥5 집단의 선택 정답 기대 비중으로는 각각 0명 0.21583%, 1~4명 0.43003%다. 앱 개수 비율만으로 성능 영향을 판단하면 안 된다.

권장 진단은 다음과 같다. 아래는 **필요한 기록의 설계**이며 완성된 모델 파일이 아니다.

| 단계 | 기록할 내용 | 얻는 정보 |
|---|---|---|
| 학습 전 | 앱별 격리 행 수·손실률·남은 train 긍정 계정 수, 원문 출처·결측 여부 | 데이터 손실과 실제로 관측되지 않은 게임을 구분 |
| 전처리/학습 후 | 토큰화 후 영벡터 여부, 학습된 공동 긍정 이웃 수 | 원문이 있어도 특징이 없는 경우, 긍정 리뷰가 있어도 연결이 없는 경우를 구분 |
| 추천 시 | 남은 긍정 입력 수·모델이 활용 가능한 입력 수·양수 점수 후보 수·실제 목록 길이 | 같은 행동 이력을 받아도 두 모델의 근거가 달라지는 이유 확인 |
| 평가 시 | 전체 지표와 지원 구간별 지표·사용자/정답 수·빈 목록 비율 | 어려운 사례를 남겨 둔 상태에서 정확도와 지원 범위를 함께 비교 |

이 기록은 관측·집계·결과표를 더 관리해야 한다는 비용이 있다. 대신 소개글 결측, 아이템 미관측, 공동 긍정 연결 없음, 사용자 프로필 부족을 하나의 ‘추천 실패’로 섞지 않고 원인을 설명할 수 있다. 지원 진단만으로 어떤 모델이 더 좋은지는 결정하지 않는다.

## 확정한 설정의 구현 순서

1. 고정 입력 37,610개 게임의 긍정 학습 이력을 구성하고 singleton 빈도를 유지한다.
2. A 소개글 우선·C 짧은 소개글 보충 원문을 만들고 전처리·문서 집합을 고정한다.
3. 숨김 후 전체 ≥5·긍정 ≥1, 동일 가중 평균, 개인화 점수만 추천·빈자리 유지, 기존 격리를 구현하고 지원 진단을 명시한다.
4. 카탈로그·소스·규칙 버전을 고정한 뒤 최종 train/validation/query/target·manifest를 저장하고 누수를 검사한다.
5. v1은 기존 TF-IDF와 후보별 K=100을 고정한 초기 베이스라인으로 학습·검증·테스트한다. 후속 전처리·이웃 설정 선택은 내부 검증에서 수행한다. 같은 고정 평가 안에서 전체·지원 구간 지표와 추천 목록 길이·빈 목록 비율을 보고한다.

학습 범위·소개글·최소 입력·집계·빈자리 처리·격리 정책은 사용자 결정으로 확정됐다. 분할 파일과 소개글 원문·토큰·TF-IDF 인덱스·코사인 검색 생성·검증을 완료했다. [콘텐츠 준비 결과](tfidf_content.md)를 참고한다. 이후 2026-11-08 Item-KNN 학습과 공통 검증·테스트도 완료했다. [모델 결과](../reports/baseline_v1.md)를 별도 기록했다. 후속 백로그는 **전체 ≥3·긍정 ≥1**, **플레이타임 등을 활용한 집계 변경**, **모델 개선 후 인기순 빈자리 보완**이며 [모델링 결정·백로그](modeling_backlog.md)에서 관리한다. 장래 변경이 평가 모집단을 확장하면 기존 테스트 예약 계정을 유지하면서 추가 예약이 필요한 계정을 재계산해야 한다.
